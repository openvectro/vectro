# The .riv format, as Vectro reads it

Vectro writes `.riv` so that every file it exports plays on Rive's free, MIT-licensed
runtimes (web, Flutter, iOS, Android) from day one. This page records what we have
confirmed by reading real files with `riv-dump`, not what we assume.

Sources: Rive's published format page (rive.app/docs/runtimes/advanced-topic/format) and
the generated headers in rive-app/rive-runtime (MIT). The closed Rive editor is never
decompiled; Rive.app is used only to export test files and to open ours.

## Layout

| Part | Encoding |
|---|---|
| Fingerprint | 4 bytes, `RIVE` |
| Major version | varuint (LEB128). Must equal 7; majors do not read each other |
| Minor version | varuint. Newer minors add features; unknown ones are no-ops |
| File id | varuint |
| Table of contents | varuint property keys ending in 0, then 2 bits per key packed into little-endian u32 words: 0 uint/bool, 1 string, 2 float, 3 color |
| Objects, to end of file | varuint type key, then (varuint property key, value)*, then 0 |

Values: uint and id are varuint; int is zigzag varuint; double is f32; color is u32;
bool is one byte; string and bytes are varuint length plus bytes. The table of contents
lists only properties newer than major 7, so a reader can skip what it does not know.

Objects have no nesting in the stream. Hierarchy comes from `parentId`, an index into
the current artboard's components; animations, keyed objects and keyframes follow
their owner in order.

## The schema

`data/rive-keys.json` holds 360 object types and 666 properties, generated by
`tools/extract_rive_keys.py` from the runtime headers. Regenerate it when Rive ships a
new minor version.

## What a real file holds

A 4.9 KB file exported by the Rive editor (format 7.0) decodes to 502 objects:

- 1 artboard (1000 x 1000) holding a boned character: 6 root bones, 5 tendons, 5 weights, 6 shapes built from 7 paths
- 8 linear animations, 40 keyed objects, 104 keyed properties, 220 keyframes, 10 cubic easings
- 1 state machine: 2 layers, 8 animation states, 11 transitions, 3 bool inputs, 6 conditions

Vector geometry is stored as vertices with in/out handles in polar form (rotation,
distance). The head is a circle of radius 57.27 drawn with four cubic vertices whose
handles are 31.63 long: the standard 0.5523 circle ratio, which confirms the decode.

All five sample files read to the last byte (502 to 850 objects each).

## Not yet covered

- Writing `.riv` (next): round-trip read then write must give identical bytes
- Embedded assets (images, fonts) inside `FileAssetContents`
- Newer features: data binding, layouts, scripting, text

## Writing: what we learned the hard way (2026-10-15)

- **Table of contents packing.** Rive starts a new u32 word every **four** keys and uses only
  its low 8 bits. Packing sixteen keys per word reads back the same but is 12 bytes short
  on a 16-key file. With four per word, all five sample files round-trip byte for byte.
- **Property names repeat across types.** `scaleX`, `value`, `name` and others exist on several
  types with different keys. Always resolve a property through the object's own type chain
  (`Schema::property_key(type, property)`), never by name alone.
- **References are indices, not ids.** `parentId`, `objectId` and listener `targetId` index the
  artboard's components (artboard = 0). `animationId` indexes the artboard's animations,
  `inputId` the state machine's inputs, and `stateToId` the states of the current layer, in file order.
- **Listeners.** `StateMachineListenerSingle` (type 114) with `targetId` and
  `listenerTypeValue` (0 enter, 1 exit, 2 down, 3 up, 4 move, 6 click), followed by its actions,
  for example `ListenerBoolChange` with `value` 0 false, 1 true, 2 toggle.
- **Bool conditions.** `opValue` 0 means "input is true", 1 means "input is false".

## Proof: a button made from scratch

`cargo run --release --example button -- tests/web/button.riv` writes a 590-byte file: one
rounded rectangle, three poses (Idle, Hover, Pressed), a state machine with `hover` and
`pressed` inputs, 150 ms blends, and four pointer listeners. Nothing in it came from the
Rive editor.

`tests/web/play.html?file=button.riv&v=<runtime version>` plays it with Rive's own web runtime.
Checked with real mouse events on 2.35.4 and 2.44.2: outside → Idle, over → Hover,
down → Pressed, up → Hover, away → Idle. The colours on screen match the file exactly.
Test pages must give the canvas a CSS size; without one, a 2× screen doubles it and the
pointer misses.

## Draw order (2026-10-15)

Rive paints components that come **earlier** in the file on top. The editor keeps the
usual convention (later in the list = in front), so the export writes shapes front-first.
Checked by overlapping two shapes and reading the pixel from Rive's runtime, both ways round.

## Paths (2026-10-15)

A path shape is a `Shape` with one `PointsPath` per outline (`isClosed`), each followed by its
vertices: `StraightVertex` when both handles sit on the point, otherwise `CubicDetachedVertex`
with handles in polar form (`inRotation`/`inDistance`, `outRotation`/`outDistance`, radians).
All outlines of one shape fill together under the `Fill`'s `fillRule` (0 non-zero, 1 even-odd),
so a ring is two circles with even-odd. Checked by importing Snap's icon SVG: Rive's runtime
draws it the same as the editor, cut-outs included.

## State machines (2026-10-16)

Proven with two files that run in Rive's web runtime with a real mouse: a loading bar driven by a
number input (`examples/loading_bar.rs`) and a whack-a-dot game (`examples/whack.rs`). Open
either in `tests/web/interactive.html?file=<riv>&sm=<machine>` to drive the inputs by hand.

- **Order.** `StateMachine`, then its inputs, then each `StateMachineLayer` with its states in
  order; a state's id is its position in the layer. Each state is followed by its blend children
  (`BlendAnimation1D`) and then its transitions (`stateToId`), each followed by its conditions.
  Listeners (`StateMachineListenerSingle` + actions) come after the layers.
- **Ids.** `inputId` indexes the machine's inputs, `animationId` the artboard's animations,
  `targetId` and `eventId` are artboard component indices. Events are components (`Event`,
  type 128, with a name and `parentId` 0), so they must be written with the shapes.
- **Transition flags.** 4 = exit time enabled (`exitTime` in milliseconds), 8 = exit time is a
  percentage, 2 = duration is a percentage, 16 = pause on exit. `duration` is the blend in ms.
- **Random.** A state with flag 1 picks among its valid transitions by `randomWeight`. Random
  timing needs several short wait states with different exit times, because only transitions
  that are valid right now take part in the draw.
- **Blend by a number.** `BlendState1DInput` (type 76) with `inputId`, then `BlendAnimation1D`
  children carrying `animationId` and the input `value` each stands for. **Set flag 2 (reset) on
  the blend state**, or Rive applies the poses one after another instead of averaging them: a
  50/50 blend of two widths then settles at two thirds, and the loading bar read 347 px instead
  of 261. With the flag it is exactly linear.
- **Conditions.** Bool: `opValue` 0 means "is true", 1 "is false". Number: op 0 equal, 1 not
  equal, 2 less or equal, 3 greater or equal, 4 less, 5 greater, plus `value`. Trigger: input only.
- **Listeners.** `listenerTypeValue`: 0 enter, 1 exit, 2 down, 3 up, 4 move, 6 click. Actions:
  `ListenerBoolChange` (`value` 0 false, 1 true, 2 toggle), `ListenerNumberChange`,
  `ListenerTriggerChange`, `ListenerFireEvent`. A listener on a shape under another shape still
  fires: the hit test is against the target's own path.
- **A note on the web runtime.** `@rive-app/canvas` 2.44 prints deprecation warnings for state
  machine inputs, state-change callbacks and event subscriptions, pointing at data binding (view
  models). They all still work; data binding is a later addition to this format reader.

## Paints (2026-10-16)

- **Gradients.** A `Fill` holds a `LinearGradient` (type 22) or `RadialGradient` (17) instead of a
  `SolidColor`, with `startX/startY/endX/endY` in the shape's own space (for radial, start is the
  centre and end a point on the rim), then `GradientStop` children (`colorValue`, `position`).
  Keying a stop's colour uses `GradientStop.colorValue` (key 38), not `SolidColor`'s 37.
- **Strokes.** `Stroke` (24) under the shape with `thickness`, `cap` (0 butt, 1 round, 2 square)
  and `join` (0 miter, 1 round, 2 bevel), then its own `SolidColor`.
- **Feather.** `Feather` (533) under a `Fill`: `strength`, `offsetX/Y`, `inner`. It is Rive's blur:
  a feathered copy behind a shape is a glow or drop shadow, `inner` gives an inset shadow.
  **Rendered by `@rive-app/canvas` 2.44 and the native runtimes; ignored by `@rive-app/webgl2`
  2.44** (the file loads, the shadows are simply absent). Vectro's editor shows it as a CSS blur.

## Follow path (2026-10-17)

A shape on a motion path carries a `FollowPathConstraint` (type 165) as a child of its `Shape` or
`Node`: `targetId` (from `TargetedConstraint`) is the component index of the path's `Shape`,
`strength` (from `Constraint`) 1, `distance` (key 363) 0..1 by arc length over all of the target's
paths, `orient` (364) turns the shape along the tangent, `offset` (365) adds the shape's own
translation to the point on the path; without it the shape's x/y are ignored. The runtime wraps
`distance` into 0..1 except that a whole number past 0 lands on the end, so 1 is the end of the path.
The target may be written after its follower, so the export fills `targetId` in once every shape has
its index. Keying `distance` animates the shape along the path. Proven with
`examples/motion_path.rs` (`tests/web/motion-path.riv`) in `@rive-app/canvas` 2.44.0: the dot's
pixels sit on the path's start (40, 160) at t=0, the middle (150, 100) at t=1 s and the end (260, 40)
at t=2 s, matching the editor's own preview to within a pixel or two.
